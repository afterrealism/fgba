Frequently asked questions

Is FGBA yet another format?§

It is an extension, not a new format: an FGBA file is a valid FlatGeobuf file with a trailer after the feature data. Every existing FGB reader — GDAL, QGIS, the JavaScript and Rust libraries — reads all features from it unchanged and never reaches the trailer (the "still a valid LAZ" principle of COPC). The only new encodings are the band records and the directory; the body, its spatial index, and its geometry are plain FlatGeobuf. See SPEC §1.

How does it compare to PMTiles?§

Different jobs. PMTiles archives baked tiles — pre-rendered raster images or pre-tiled, clipped, simplified vector geometries — for display at fixed zoom levels. FGBA keeps live features: the full-fidelity geometries stay in the body for styling, querying, and download at any zoom, and the trailer adds counts per equal-area cell for low-zoom overviews and count analytics ("how many features are in this region") that a tile archive cannot answer. Bake tiles when you need scale-proof cartography; serve FGBA when the data itself must stay queryable.

How does it compare to FGBO?§

FGBO (FlatGeobuf Overviews) appends simplified-geometry overviews so renderers can draw a light version of the data at low zoom. FGBA appends aggregations — counts in A5 cells — so renderers can draw an exact density overview and analytics can answer counts without reading features. They solve different halves of the low-zoom problem, and FGBA's trailer conventions deliberately follow FGBO's. The designs are meant to compose: a file can only have one EOF footer, so the FGBA directory is a kind-tagged table that can list FGBO sections under registered kinds, discovered by the FGBA footer (SPEC §10.4).

How does it compare to GeoParquet?§

GeoParquet is a columnar analytics format: it shines inside query engines (DuckDB, Arrow-based stacks) doing scans, filters, and joins over many columns. FGBA is a serving format: a single file behind plain HTTP range requests that a map viewer or a small client opens with 3 requests, no query engine involved. GeoParquet has no per-zoom aggregate bands; FGBA has no columnar predicate pushdown. If your workflow is "analyze the table", use GeoParquet; if it is "put the dataset on static hosting and render/count it at every zoom", use FGBA.

Why A5 cells?§

A5 is a pentagonal discrete global grid. Three properties make it the right binning for aggregates:

  • Equal area. At one resolution every cell is an equal-area pentagon, so a count per cell is an honest density — comparing cells needs no area correction.
  • Curve-ordered IDs. Cell IDs follow a space-filling curve, so spatially adjacent cells are numerically adjacent; a viewport covering is a few contiguous runs of the sorted records (measured 1–7 runs) — few seeks, few range requests.
  • Frozen IDs. A5 cell IDs are frozen by the A5 project from v1.0, so files written today refer to the same cells forever (SPEC §11).

Why not H3?§

H3's grid mixes hexagons with 12 pentagons, and cell areas vary within a resolution — fine for indexing, but a count per cell is no longer directly comparable across the map. A5's topology is a single family of equal-area pentagons at every resolution, which is exactly what aggregate counts want. (A5 also gives the curve-ordered IDs above.) Nothing about FGBA's directory precludes a future H3 band kind — the grid byte in each band header leaves that door open — but the reference implementation builds A5 bands only.

The file breaks my JavaScript FGB reader?§

Only on one path, by design. Index-driven reads (bbox queries, HTTP range streaming) structurally never reach the trailer. Sequential readers that respect FlatGeobuf's features_count stop before it. The one caveat is the flatgeobuf JS full-scan path, which ignores features_count: it yields all features, then hits the trailer's 4-byte sentinel. The sentinel (FF FF FF FF) is chosen so that path fails fast — it parses as an impossible ~4 GiB feature length — instead of silently misparsing trailer bytes as features (SPEC §4.1, §10.1). The measured matrix: Rust flatgeobuf 6.0.1 ✅, GDAL/OGR 3.12 ✅, JS 4.4.0 index paths ✅, JS full scan ⚠️ fails fast after the features. An upstream featuresCount fix is the remedy; until then, use bbox queries in JS.

Can I update an FGBA file in place?§

No — the format is write-once. Implementations must not append to or partially rewrite a file; rebuild it from the source instead (SPEC §4). This is what makes the bytes deterministic and safe to cache forever on a CDN. The same applies to the CLI: fgba build on a file that already has a trailer rebuilds the trailer from the body rather than patching it.

What if the trailer is corrupt?§

The body is never hostage to the trailer. A bad footer CRC, malformed directory, or invalid band means the reader falls back to reading the file as plain FlatGeobuf — every feature is still there (SPEC §10.2). Trailer bytes are treated as hostile input: every count and length is bounded before allocation, and nothing panics (SPEC §12).
