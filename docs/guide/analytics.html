Native SQL & analytics

fgba query runs native, read-only DataFusion SQL over local FlatGeobuf and FGBA files through the fgba-sql crate. It streams CSV to stdout and needs no external database service or intermediate analytical format. Remote SQL URLs are not currently supported.

Quickstart§

Install the CLI, count exact body rows, and group preserved properties:

cargo install fgba-cli
fgba query cities.a.fgb "SELECT COUNT(*) FROM features"
fgba query cities.a.fgb "SELECT \"name\", COUNT(*) FROM features GROUP BY \"name\""

With --bbox, register the explicitly approximate viewport covering. This example counts selected cells and sums their stored counts:

fgba query cities.a.fgb --bbox -10,40,10,60 "SELECT COUNT(*) AS cells, SUM(count) AS estimated FROM a5_viewport_approx"

For numeric property statistics, use an indexed FlatGeobuf fixture that has a numeric height column, here called cities-metrics.fgb:

fgba build cities-metrics.fgb --analytics --chunk-rows auto -o cities-metrics.a.fgb
fgba query cities-metrics.a.fgb "SELECT name, row_count, non_null_count, null_count, min_f64, max_f64 FROM attribute_stats WHERE name='height'"

The name-only 12-city cities.a.fgb fixture is different: its name property is opaque, so it has exact null counts but no numeric bounds or sum. Do not expect min_f64, max_f64, or sum_text for that column.

Interactive workspace§

The local Range Lab in example/ provides the complete upload → conversion → map → SQL workflow. It is a local Node server, not a feature of the static documentation host:

cargo build -p fgba-cli
cd example
npm start
# open http://127.0.0.1:8090
  1. Choose Upload vector and select GeoJSON, CSV/TSV, FlatGeobuf, or a Shapefile with its .shx sidecar (plus .dbf for attributes).
  2. Set a new .a.fgb name, choose rows per analytical chunk, and keep analytics enabled when you want property/geometry zone maps and Arrow-backed SQL scans.
  3. Conversion opens the new object in the uploads bucket on the existing map. Choose SQL query for exact rows, counts, attribute_stats, and optional viewport bbox/resolution queries.

Uploads are stored locally and never overwrite an existing object. SQL is read-only, coordinates must already be WGS 84 lon/lat, and conversion is done by the native CLI rather than a browser-side mock.

Tables and exactness§

TableMeaning
featuresExact FlatGeobuf body rows with typed properties, nullable geom_wkb, and seven nullable geometry outputs: geom_length, geom_area, geom_npoints, bbox_xmin, bbox_ymin, bbox_xmax, and bbox_ymax. The first three have SQL-only names for the stored kind-3 length, area, and npoints metrics; the bbox columns retain their stored names.
a5_band_<res>Integral cell_id/count records from an available kind-1 band. Each count is exact for that cell under bounding-box-midpoint attribution, not a geometry-intersection count.
a5_viewport_approxThe cells returned by Reader::query for the supplied --bbox and --res (deepest band by default). The selected cells and their stored counts are exact; their sum is only a regional estimate.
attribute_statsExact global kind-2 metadata when that optional section exists: row/null/NaN counts, typed nullable bounds, sum_text, and validity flags. It reads no Arrow payload.
 
SELECT "name", geom_wkb, bbox_xmin, bbox_ymin, bbox_xmax, bbox_ymax
FROM features LIMIT 100;

SELECT SUM(count) AS midpoint_attributed_total FROM a5_band_2;

SELECT name, nan_count, sum_text, sum_valid, has_infinity
FROM attribute_stats WHERE name = 'height';

COUNT(*) FROM features is an exact body-row count. Only the narrow Projection → Aggregate(count(1)) → TableScan logical plan, optionally with a literal limit or canonical bbox filter, uses the header or R-tree metadata shortcut. Other counts and filters execute normally. A whole band's sum covers features successfully assigned by midpoint; a viewport covering can overcount or undercount true regional geometry matches and has no general error bound.

When a viewport's spherical area is at least half the sphere, Reader::query conservatively filters the band's own cells by longitude/latitude bbox overlap instead of constructing ambiguous direct or complement spherical ring coverings. This avoids the near-world covering failure mode; it does not make band sums exact geometry-intersection counts or establish a global correctness bound.

Bbox columns express bbox intersection, not exact geometry intersection. WKB is geometry data, not a CRS-aware SQL type. The st_length(Binary), st_area(Binary), and st_npoints(Binary) UDFs return Float64, Float64, and UInt32 planar metrics over supported standard WKB, using the same XY definitions as kind 3. They perform no CRS transformation. A NULL argument returns NULL; an empty WKB geometry returns 0.0, 0.0, and 0, respectively, unlike the NULL stored kind-3 values for an empty geometry. Malformed or unsupported WKB is a query error. Preserve and manage CRS semantics outside these SQL operators.

Arrow execution and metadata§

For ordinary full or zone-pruned scans, projections containing only properties, geometry metrics, and/or stored bbox columns read just the required independent Arrow IPC chunks and validity. These columnar scans split chunks across DataFusion target partitions. Direct R-tree-only selections remain single-partition.

Mixed WKB/metric projections and SELECT * deliberately use exact body execution. Selecting WKB, using a file without usable kind-2 analytics, or reading bbox columns without usable kind 3 also falls back to the streaming row-oriented FlatGeobuf body. Explicit geom_length, geom_area, or geom_npoints projections without valid kind 3 fail during planning with guidance to rebuild using --geometry-metrics; the WKB UDFs above are the body-backed alternative. Results stream as CSV with one header; the CLI does not collect the complete result.

--scan-threads controls DataFusion target partitions for analytical chunk scans. Row order is unspecified unless the query has ORDER BY. Multi-partition floating-point aggregates may reassociate and differ in low-order bits, so any relative tolerance must be chosen for the data. Stored kind-2/kind-3 global statistics remain deterministic sequential body-order accumulations.

A valid bbox filter is Exact for bbox intersection through the existing FlatGeobuf packed R-tree. Numeric/null zone maps are always candidate filters: DataFusion retains and applies the residual attribute predicates on surviving rows. This is why no second spatial index is created — the existing R-tree selects spatial candidates, kind-2/kind-3 zone maps prune chunks, and exact kind-2 body offsets locate any required feature ranges.

Missing, unsupported, or malformed optional metadata disables only the affected acceleration; for example, malformed kind 3 leaves valid kind 2 usable. Queries that can proceed without that acceleration use the exact body. A malformed Arrow payload falls back to its exact body range per chunk, without invalidating other chunks, the body, or kind-1 bands.

Null and NaN are distinct: null_count = row_count - non_null_count, while NaN is non-null. Float bounds exclude NaN but include infinities; all-null/all-NaN values have no numeric bounds and still count as rows. Opaque values have no numeric bounds or sum. sum_text preserves a valid stored sum as exact metadata text; it is not a license to replace arbitrary SQL aggregation, and invalid sums are null.

Optional kind-2 and kind-3 layouts§

--analytics on build or convert writes kind-2 BODY_ANALYTICS and, by default, kind-3 GEOMETRY_METRICS when at least one property column exists. --geometry-metrics also enables analytics; --no-geometry-metrics opts out of kind 3 while retaining kind 2. A property-free body gets neither optional section. An ordinary build without these flags is unchanged, and neither the footer format nor directory version changes.

Kind 2 stores each property column's 56-byte global statistic, 24-byte statistics per fixed-row chunk, independent Arrow IPC chunks, and shared absolute FlatGeobuf body chunk offsets. Kind 3 reuses the same row_count, chunk_rows, and chunk_count and contains exactly seven derived columns, without a second body-offset array. The reference writer places kind 2 first, kind 3 second, and kind-1 bands last; readers find them by directory kind, not physical order.

Stored kind-3 nameSQL nameType and meaning
lengthgeom_lengthFloat64 planar degree-unit length, including every Polygon exterior and interior ring

The bbox values are the geometry's exact finite coordinate envelope. An empty or absent geometry has NULL in all seven stored columns, although its row still counts in kind 2 and stays on the shared chunk grid. A non-empty Point has non-null zero length and area. These are planar WGS84 longitude/latitude metrics, not geodesic measurements or CRS transformations.

--chunk-rows auto is the CLI default and adapts the chunk height to the feature count. An explicit positive --chunk-rows size overrides automatic sizing; the selected height is stored in the sections and is not a format constant. The byte-level records and offset formulas are in SPEC §6A and SPEC §6B.

Pruning and resource tuning§

Zone maps help when values are clustered and predicates selective. Random or unclustered values can give every chunk overlapping min/max bounds, while opaque columns have no numeric zone maps; those queries need full candidate scans. Statistics do not make high-cardinality groups, distinct values, sorts, joins, medians, or quantiles cheap or memory-free.

Rebuild with an explicit smaller --chunk-rows for finer pruning at the cost of more metadata, Arrow files, and range reads. Larger chunks reduce that overhead but admit more candidate data. Body ranges separated by at most 64 KiB are merged, so skipped bytes inside a small gap can still be decoded; larger gaps remain separate ranges. Tune chunking against actual result parity, bytes read, and ranges opened rather than expecting every filter to prune.

Source row/byte batch limits are not a whole-query memory budget. Arrow and DataFusion operators still hold working state, and one oversized feature can exceed a source batch target. Correct, complete results take precedence over returning a partial aggregate.

The file-oriented fgba build path streams the body and spooled sections directly into atomic output. Anonymous temporary files hold Arrow IPC chunks instead of retaining complete analytical sections or the trailer in memory. Chunk metadata, band midpoint data, and per-band records still consume memory; spooling is not a constant-memory guarantee for the whole build.
