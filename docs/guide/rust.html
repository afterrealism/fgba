Reading from Rust

The fgba crate reads the trailer of an FGBA file from any Read + Seek source — a local file, an in-memory buffer, an HTTP range reader. The FlatGeobuf body stays the business of the flatgeobuf crate. Full API reference: docs.rs/fgba.

cargo add fgba           # core reader/writer
cargo add fgba --features http  # + HTTP range reading (native)
cargo add fgba --features analytics  # + kind-2 statistics / Arrow IPC
Version 0.1 implementing the draft v1 specification. Optional kind-2 BODY_ANALYTICS sections hold exact global statistics, per-chunk zone maps and body offsets, and independent Arrow IPC property chunks. Missing or malformed analytics disables only this acceleration; the exact FlatGeobuf body remains the fallback and kind-1 bands stay readable.

Local files§

Reader::open_path opens a local file buffered. Opening is two small reads at end-of-file: the 32-byte footer, then the CRC-verified directory. A file without the FGBAGG01 magic returns Error::NotFgba — treat it as plain FlatGeobuf (SPEC §10.2).

let mut r = fgba::Reader::open_path(std::path::Path::new("cities.a.fgb"))?;
println!("body is {} bytes; the trailer starts there", r.body_len());

// The band ladder: which A5 resolutions carry aggregates.
for band in r.bands() {
    println!("res {}: {} bytes at offset {}", band.res, band.size, band.offset);
}

Bands, queries, stats§

  • read_band(res) — read and fully validate one band: (cell_id, count) records, ascending cell IDs, counts summing to total_features (SPEC §6 validation rules).
  • query(view, res) — the band records whose cells cover a viewport [min_x, min_y, max_x, max_y] in lon/lat degrees. The covering uses overlapping containment (SPEC §9.4).
  • stats(view, res) — count-only: occupied cells and estimated feature total, without returning the records.
// Count analytics over Europe — a few hundred bytes read, no features touched.
let europe = r.stats([-11.0, 35.0, 31.0, 71.0], 2)?;
println!("{} cells, ~{} features", europe.cells, europe.total);

// The raw (cell, count) records over New York.
for (cell, count) in r.query([-75.0, 39.0, -72.0, 42.0], 2)? {
    println!("cell {cell:#018x}: {count} features");
}

Viewport latitudes of exactly ±90° degenerate the A5 covering; clamp to the Web Mercator range (±85.0511°) for world views — see SPEC §9.4 step 0.

Reading features from the body§

The body is a plain FlatGeobuf file. Reader::body() hands you the underlying source positioned at offset 0; open it with the flatgeobuf crate and run bbox queries as usual. Read only offsets below body_len() — everything beyond is the trailer.

use flatgeobuf::FgbReader;

let mut r = fgba::Reader::open_path(std::path::Path::new("cities.a.fgb"))?;
let mut fgb = FgbReader::open(r.body()?)?;
// fgb.select_bbox(minx, miny, maxx, maxy)? — the standard FlatGeobuf API

Over HTTP range requests§

With the http feature, Reader::open_url adapts a remote file to a blocking Read + Seek source over RFC 9110 range requests (SPEC §9.2). The server must answer 206 Partial Content — see Hosting for what that requires of your bucket or CDN.

// Cargo.toml: fgba = { version = "0.1", features = ["http"] }
let mut r = fgba::Reader::open_url("https://example.com/buildings.a.fgb")?;
let cells = r.query([-0.5, 51.3, 0.3, 51.7], 7)?;
let total = r.stats([-180.0, -85.0, 180.0, 85.0], 2)?.total;

Opening costs 3 requests: the Range: bytes=0-0 probe (which also yields the file length), the 32-byte footer, and the directory. Open plus the first band therefore costs 4 requests. query and stats cache one most-recently-used band: repeated same-resolution calls issue no further band request, but changing resolution evicts it and switching back fetches the earlier band again. read_band(res) always performs a fresh decode. The HttpRangeReader counts its own traffic for diagnostics:

let http = r.into_inner();
println!("{} requests, {} bytes read", http.requests(), http.bytes_read());

Hardening (SPEC §12): a 60-second per-request timeout, at most 5 redirects, https only — with http allowed for loopback hosts — and https→http downgrades refused. A non-206 answer mid-read is an error naming range support, never a silent full-body read.

WebAssembly§

Blocking I/O does not exist in the browser, so the read is two-phase (SPEC §9.3): compute the byte ranges needed (footer, directory, band slice), fetch them asynchronously with fetch and a Range header, then decode from memory. SliceReader wraps fetched bytes as a seekable source, so the same Reader used for files and HTTP decodes them unchanged.

// Phase 1 (async, your code or the JS host): fetch the needed ranges.
let bytes: Vec<u8> = fetch_range(url, start, end).await;

// Phase 2 (sync): decode as usual.
let mut r = fgba::Reader::open(fgba::SliceReader::new(bytes))?;
let stats = r.stats([-180.0, -85.0511, 180.0, 85.0511], 2)?;

The wasm canvas demo implements the whole loop in plain JavaScript — footer, CRC-verified directory, one band — against plain static hosting.
