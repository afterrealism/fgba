Hosting FGBA files

FGBA streams off plain static hosting — no server-side code. The host must support HTTP range requests; if a browser viewer lives on a different origin, it must also answer a CORS preflight. This page mirrors SPEC §9.2 and flatgeobuf.org's CDN notes.

The one hard requirement: 206§

Readers open a file with a one-byte probe, Range: bytes=0-0. The server MUST answer 206 Partial Content with a Content-Range header — that header is also how the reader learns the file length. A 200 answer means the host does not do range requests, and the reader fails with a message naming range support. S3, R2, nginx, and most static hosts qualify.

Check a host by hand:

$ curl -o /dev/null -D - -H 'Range: bytes=0-0' \
    https://example.com/data/buildings.a.fgb
HTTP/2 206
content-range: bytes 0-0/128456789
accept-ranges: bytes
content-length: 1

Range support lets a reader open a file of any size with 3 requests (probe + 32-byte footer + CRC-verified directory) and then fetch each aggregate band once — see the measured numbers.

Cross-origin reads from browsers: CORS§

Native readers (the Rust library, GDAL, QGIS) do not care about CORS. Browsers do, when the page and the data sit on different origins. Three things must line up:

  1. Access-Control-Allow-Origin on the responses — your viewer's origin, or * for public data.
  2. The Range preflight. Range is not a CORS-safelisted request header, so the browser sends an OPTIONS preflight before the first range request. The host must answer it with Access-Control-Allow-Headers including Range. Send Access-Control-Max-Age (e.g. 86400) so browsers cache the preflight — without caching, every range request pays a second round trip.
  3. Access-Control-Expose-Headers including Content-Range (and Accept-Ranges, Content-Length, ETag are useful too). Without it, JavaScript can read the 206 body but not the Content-Range header, and FGBA readers cannot learn the file length.

Test the preflight by hand:

$ curl -X OPTIONS -D - -o /dev/null \
    -H 'Origin: https://viewer.example' \
    -H 'Access-Control-Request-Method: GET' \
    -H 'Access-Control-Request-Headers: range' \
    https://example.com/data/buildings.a.fgb
HTTP/2 204
access-control-allow-origin: https://viewer.example
access-control-allow-headers: range
access-control-max-age: 86400

S3§

S3 answers range requests natively. Attach a CORS configuration to the bucket (console → Permissions → CORS, or PutBucketCors):

[
  {
    "AllowedOrigins": ["https://viewer.example"],
    "AllowedMethods": ["GET", "HEAD"],
    "AllowedHeaders": ["range"],
    "ExposeHeaders": ["content-range", "accept-ranges", "content-length", "etag"],
    "MaxAgeSeconds": 86400
  }
]

For public, cross-origin-readable data, "AllowedOrigins": ["*"] works.

Cloudflare R2§

R2 answers range requests and speaks the same S3-shaped CORS policy (dashboard → bucket → Settings → CORS Policy, or the S3 API):

[
  {
    "AllowedOrigins": ["https://viewer.example"],
    "AllowedMethods": ["GET", "HEAD"],
    "AllowedHeaders": ["range"],
    "ExposeHeaders": ["content-range", "accept-ranges", "content-length", "etag"],
    "MaxAgeSeconds": 86400
  }
]

nginx§

nginx serves byte ranges for static files by default; add the CORS headers and short-circuit the preflight:

location /data/ {
    add_header Access-Control-Allow-Origin  "$http_origin" always;
    add_header Access-Control-Allow-Methods "GET, HEAD, OPTIONS" always;
    add_header Access-Control-Allow-Headers "Range" always;
    add_header Access-Control-Expose-Headers \
        "Content-Range, Accept-Ranges, Content-Length, ETag" always;
    add_header Access-Control-Max-Age 86400 always;
    if ($request_method = OPTIONS) { return 204; }
}

(For world-public data, use * instead of $http_origin and drop the if's special status — add_header ... always already covers preflights.)

In front of a CDN§

flatgeobuf.org's Optimizing Remotely Hosted FlatGeobufs notes apply to FGBA unchanged: range reading makes many small requests, so round-trip latency — not throughput — dominates, and a caching CDN close to the viewer helps. One gotcha named there: popular CDNs such as CloudFront support range requests but do not cache the preflight OPTIONS responses by default — enable OPTIONS caching (the response headers are what vary), or every range fetch pays the preflight round trip. See flatgeobuf.org and the CloudFront docs on CORS header caching.

Cache forever, rebuild to change§

FGBA files are write-once and deterministic: identical input and options produce byte-identical files, and updates are rebuilds, not edits (SPEC §8). So publish under a new key/name and set a long cache policy on the data:

Cache-Control: public, max-age=31536000, immutable

A reader that falls back or a file that fails verification is almost always a hosting issue, not a format issue — run the 206 probe and the preflight check first. One known non-hosting caveat: re-saving through another tool (ogr2ogr) drops the trailer — distribute the file as built (SPEC §10.3).
